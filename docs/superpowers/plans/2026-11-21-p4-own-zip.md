# P4 slice 2: a player's own ZIP, read safely, and one disc identity

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The server and the page take the same discs and give them the same identity, whatever the source: a folder on the host, a player's own CUE and BIN files, or a player's own ZIP. The page reads a player's ZIP safely (stored and deflated entries, a CUE in a folder of the archive, bounded sizes, each entry's checksum) and refuses what DATA-04 lists with a clear error; an exact copy of the server's archive keeps its fast path. DATA-03 and DATA-04 from the brief, and DATA-02 for the modules.

**Architecture:** One module of the page, `web/disc-sheet.js`, holds the rules of a disc: how a CUE sheet names its tracks, how a name is matched, and the bounds. The server's `findDisc` and the page's `selectedDisc` both use it, and so will the ZIP reader. The disc identity stays the existing algorithm (SHA-256 of the JSON of `[name, size, sha256]` for the CUE and then its tracks in CUE order; brief §11.3). A fixture file that both test suites read pins it, with identities taken from the Python launcher's implementation. The ZIP reader, `web/disc-zip.js`, reads the archive's central directory, checks every entry it uses, and hands the emulator the CUE and its tracks as separate files, as the player's own files are handed today; it never writes a file and never passes an arbitrary archive to the emulator's own extractor. An exact copy of the server's archive (its size and chunk checksums, D74) is passed as it is, as today.

**Tech Stack:** Node.js 26.13.1 single executable, TypeScript checked only, `node:test`. The page's modules are plain JavaScript and run in Node for their tests (`Blob`, `File`, `crypto.subtle`, `DecompressionStream`).

**Spec:** the owner's brief "Sled Storm Server — Node SEA", sections 11.2, 11.3 and 15.2 (DATA-02, DATA-03, DATA-04), outside the repository, and `docs/sea-server-plan.md`, "P4 Independent data sources".

**Review base:** the state that P4 slice 1 left, the ignored file `.superpowers/sdd/p4-slice-1-tree.tar`. On 2026-11-21, before the first change of this slice, all 212 files that Git does not ignore were equal to it, byte for byte. A commit of P3 and P4, if the owner asks for one, replaces it.

## Decisions taken with this plan

1. **The page takes any disc the server takes (D75).** One CUE whose `FILE "…" BINARY` lines name from 1 to 99 distinct tracks beside it. The rule that the CUE lists eleven tracks goes: whether a disc fits a room is the disc identity's question (ROOM-05), and the features of the PAL disc stay behind `pal`. This settles the first item of "Open after slice 1": a host whose disc is not the Europe one can host under `local-only`, and a guest with the same files joins. Cost: in the Python launcher's local-file mode, players can load a disc other than the Europe one, as its shared mode already allows; none is tested.
2. **Bounds shared by the server and the page (D76).** A CUE of at most 1 MiB; at most 99 `FILE` lines (a CD holds at most 99 tracks); the CUE and its tracks together at most 1 GiB (a 99-minute CD is 1,047,816,000 bytes raw). Both check them before reading a file. The ZIP reader adds its own bounds in phase 2. Cost: a folder larger than any CD, which is no PlayStation disc, is refused by the server where it was taken before.
3. **A track is found by its name in NFC and lower case (D77).** A CUE that names a track in another case or normalization than its file finds it, as the server already does on a macOS volume; two tracks that match one name are a track listed twice. The identity counts each track under the name the CUE spells and the CUE under its own file's name, as before. Cost: on a case-sensitive volume the server would not find such a track while the page would; the host is macOS, whose volumes are case-insensitive unless chosen otherwise.
4. **Shared fixtures with an independent oracle (D78).** `web/disc-identity.fixtures.json` lists discs of synthetic bytes with their identities, and discs that the shared rules refuse with the message. `server/scripts/disc-fixtures.py` writes it, computing each identity with the Python launcher's algorithm (`server.py`, `shared_identity`: `json.dumps(manifest, ensure_ascii=False, separators=(',', ':'))`), an implementation independent of both the server's and the page's. The page's tests and the server's tests read it; the bundle leaves it out, as every `*.fixtures.json`. Cost: no fixture has the PAL flag, which needs the real first data track.

Each used entry's local header must name it as its central record does and its data must lie inside the file, before the central directory and apart from the other used entries.
- Each used entry is read once through a counting stream: inflated for method 8, sliced without a copy for method 0; more bytes than declared stop it at once, fewer or a wrong CRC-32 refuse it.

## Review Focus

1. No archive, however built, makes the page read beyond the file, keep more than one entry's bytes at once, inflate past a declared size, or hand the emulator a name that leaves the CUE's folder.
2. A damaged archive is refused with a clear error and never played; nothing falls back silently to another source.
3. The server and the page give one identity for one disc, whatever the source, and the algorithm is the one of 1.1.0.
4. The exact copy of the server's archive still takes its fast path, and a guest under `local-only` gets no new way to the host's disc.
