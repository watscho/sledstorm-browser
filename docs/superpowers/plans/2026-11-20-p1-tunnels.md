# P1 Slice 2: Quick Tunnels Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** The packaged server starts the existing Cloudflare Quick Tunnel and its mirror by itself, knows when the public address really works, recovers within bounds and hands out the private link.

**Architecture:** A pinned `cloudflared` ships as a resource. One supervisor class runs it, reads readiness from its metrics listener instead of its log, restarts it with bounded backoff, and reports a state. The host service runs two of them (primary and mirror) beside the local stack and feeds the public address to `/session-info` and the gateway from memory.

**Tech Stack:** as slice 1, plus `cloudflared` 2026.10.7 for macOS arm64.

**Spec:** `docs/sea-server-plan.md` (stage P1, slice 2) and the owner's brief (not in the repository), section 10 and checks TUN-01 and TUN-02.

## Global Constraints

- Everything in the slice 1 plan's Global Constraints still applies.
- The tunnel hostname and the access token are parts of a private link. They never reach a log, the status, a test fixture or a document. The link leaves the server in two ways only: through the authorized `GET /api/invitation`, and through the `X-Invite-Origin` and `X-Invite-Path` headers of `/session-info` on the loopback game origin, which the host page needs to build invitations, as with `server.py`.
- Automated tests never start a real tunnel and never use the network. A fake `cloudflared` and an injected probe stand in.
- A real tunnel is opened only by hand, only in front of synthetic resources and a synthetic disc.
- Transport behavior is unchanged: the same `cloudflared tunnel --url … --protocol … --no-autoupdate` commands as `tools/play-online.py`, the primary to the gateway and the mirror with `--protocol http2` to the gateway's mirror listener.

## Facts measured before planning (cloudflared 2026.10.7, 2026-11-20)

- The release notes list the SHA-256 of the binary; the GitHub asset digest is the SHA-256 of the `.tgz`. Both were checked against the download.
- `--metrics 127.0.0.1:<port>` serves `/ready` (200 with `readyConnections` once a connection is registered, 503 before) and `/quicktunnel` (`{"hostname":"….trycloudflare.com"}`).
- SIGTERM ends the process with exit code 0. An empty `HOME` works and nothing is written there.
- A new hostname appeared in public DNS about five seconds after `/ready`. Its zone has a negative TTL of 60 s, so asking the system resolver too early makes this computer fail to open the link for a minute. HTTPS through the tunnel worked as soon as the name resolved.

## Review Focus

1. `cloudflared` never becomes ready (no network): the start must end in a failed tunnel within its deadline and leave no process. Test in Task 3.
2. `cloudflared` dies while hosting: bounded restarts, a new address, and the old address is no longer handed out meanwhile. Tests in Task 3 and Task 5.
3. The server stops or is killed while a tunnel starts or runs: no orphan `cloudflared`. Tests in Task 3 and Task 6.
4. The mirror cannot start: the host still comes online with the primary. Test in Task 5.
5. The hostname or token leaking into the log or the status. Tests in Task 3 and Task 5.

### Task 3: Tunnel supervisor

**Files:**
- Create: `server/src/tunnel.ts`, `server/test/fake-cloudflared.mjs`
- Test: `server/test/tunnel.test.ts`

**Interfaces:**
- Produces:
  ```ts
  export type TunnelState = 'off' | 'starting' | 'online' | 'retrying' | 'failed';
  export interface TunnelOptions {
    name: string;
    /** The program and leading arguments; the supervisor appends the tunnel arguments. */
    command: { command: string; args: string[] };
    /** Loopback port that the tunnel exposes. */
    port: number;
    protocol: string;
    homeRoot: string;
    log: Log;
    /** Rejects while the public address does not work yet. Absent: ready is enough. */
    probe?: (origin: string, signal: AbortSignal) => Promise<void>;
    onChange?: () => void;
    timing?: Partial<{ readyMs: number; probeMs: number; pollMs: number; lostMs: number; restartDelaysMs: number[]; stableMs: number; graceMs: number }>;
  }
  export interface Tunnel { state(): TunnelState; /** `https://<hostname>` while online, else null. */ origin(): string | null; start(): void; stop(): Promise<void> }
  export function createTunnel(options: TunnelOptions): Tunnel
  ```
- Defaults: `readyMs` 90 000, `probeMs` 60 000, `pollMs` 250 while starting and 2 000 while online, `lostMs` 20 000, `restartDelaysMs` [2 000, 4 000, 8 000, 16 000, 30 000], `stableMs` 60 000, `graceMs` 5 000.

**Behavior.** Each launch gets a free metrics port and an empty private `HOME` under `homeRoot`; the child gets `tunnel --url http://127.0.0.1:<port> --metrics 127.0.0.1:<metrics> --protocol <protocol> --no-autoupdate`. `starting` until `/ready` answers 200 with `readyConnections >= 1`, `/quicktunnel` gives a hostname matching `^[a-z0-9-]+\.trycloudflare\.com$`, and the probe resolves; then `online`. A launch that misses `readyMs` or `probeMs`, or whose process exits, is stopped and counts as one failure. After a failure the state is `retrying` and the next launch waits the next delay; when the delays are used up the state is `failed` and nothing more is started until `start()` is called again. A launch that stayed online for `stableMs` resets the delays. While online, `/ready` not answering 200 for `lostMs` counts as a failure. `origin()` is null in every state but `online`. `stop()` ends the child (SIGTERM, then SIGKILL after `graceMs`), cancels timers and ends in `off`. The log names states only.

The fake program serves the two metrics routes and takes its script from `FAKE_CLOUDFLARED`, a JSON object: `readyAfterMs`, `neverReady`, `exitAfterMs`, `exitCode`, `badHostname`. Its hostname is `synthetic-<pid>.trycloudflare.com`.

- [x] **Step 1: Failing tests**, all with short timings: `a tunnel comes online and reports its address`; `the address is hidden until the probe passes`; `a tunnel that never becomes ready fails within its deadline and leaves no process`; `a tunnel that dies is restarted with a new address`; `restarts are bounded and a new start tries again`; `a lost connection counts as a failure`; `a hostname outside trycloudflare.com is refused`; `stop during a start leaves no process`; `the log names neither the address nor the metrics port`; `the child gets the launcher's arguments and a private empty home`.
- [x] **Step 2: Run** `node --test server/test/tunnel.test.ts`. Expected: fails, module not found.
- [x] **Step 3: Implement** on `startOwnedProcess` from Task 2.
- [x] **Step 4: Run** the file and the type check. Expected: pass.

### Task 4: Probe of the public address

**Files:**
- Create: `server/src/tunnel-probe.ts`
- Test: `server/test/tunnel-probe.test.ts`

**Interfaces:**
- Produces:
  ```ts
  /** Resolves to an IPv4 address once public DNS knows the name. Never asks the system resolver. */
  export function resolvePublic(hostname: string, signal: AbortSignal, options?: { resolve4?: (name: string) => Promise<string[]>; intervalMs?: number }): Promise<string>
  /** Checks the gateway behind `origin`: the access link, an allowed page and a Netplay round trip that takes no seat. */
  export function probeGateway(origin: string, accessToken: string, options?: { address?: string }): Promise<void>
  /** The production probe: resolvePublic, then probeGateway pinned to that address, repeated until it passes or `signal` aborts. */
  export function publicProbe(accessToken: string): (origin: string, signal: AbortSignal) => Promise<void>
  ```
- `resolvePublic` uses `dns.promises.Resolver` with servers `1.1.1.1` and `1.0.0.1`, retries every `intervalMs` (default 1 000) on `ENOTFOUND` and `ENODATA`, and rejects with the signal's reason when aborted.
- `probeGateway` expects: `GET /access/<token>` answers 302 and sets `sled_access`; `GET /session-info` with that cookie answers 200 with JSON; a WebSocket to `/netplay` with the cookie and `Origin: <origin>` accepts `{ role: 'check', room, token }` for a random room and closes with code 1008. `address` pins every connection to that IP while keeping the host name for TLS and `Host`.

- [x] **Step 1: Failing tests.** `the probe passes against a running gateway and relay` (a host service without tunnels, origin `http://127.0.0.1:<gatewayPort>`); `the probe fails for a wrong token, a closed port and a gateway without its relay`; `public DNS is asked again until the name exists` (injected resolver: two `ENOTFOUND`, then an address); `a resolver failure of another kind is passed on`; `an aborted wait stops asking`.

**Behavior.** After the local stack is up the service starts the primary tunnel to the gateway port and, without waiting, the mirror tunnel to the gateway's mirror port with protocol `http2` and no probe. Host state: `starting` until the primary is `online` or `failed`; `online` only with the primary online; `degraded` with a `tunnel` problem while the primary is `retrying` or `failed` (`The public address is not available. The game still works on this computer.`). The mirror never changes the host state. `/session-info` on loopback carries `X-Invite-Origin` and `X-Invite-Path` only while the primary is online; the gateway's `getMirrorOrigin` returns the mirror origin only while the mirror is online. `stop()` ends both tunnels before the local stack. A missing `bin/cloudflared` gives a failed tunnel with `This build has no tunnel program.`
